# 《RailGo-Flutter 三视角安全与可用性审计报告》

> 审计对象：`main` 分支 @ `c877d8e`（Phase 2 架构与代码生成进展中）
> 审计视角：**USER 用户体验** / **蓝队（防御纵深）** / **红队（攻击模拟）**
> 审计方式：本地人工深度静态审查（本机无 Flutter SDK；`flutter analyze` / `flutter test --coverage` 权威验证由 GitHub Actions `ci.yml` 承担）
> 修复基线：本报告"本轮修复"列标注 ✅ 的条目已在同批提交中落地；标注 📋 的条目为后续迭代待办。

## 0. 执行摘要

整体架构质量良好：SM4-CBC + 随机 IV 的本地加密、门禁先于敏感操作、防篡改时钟、限流三件套等设计在同类移动端项目中属上游水准。但本次三视角审计仍发现 **14 项值得处理的问题**：

- **红队高危 2 项**：服务源 URL 不校验协议（可被诱导降级为 HTTP 明文传输）；PIN 验证无尝试次数限制（6 位数字空间可在数小时内穷举）。
- **红队中危 3 项**：PIN 哈希算法选型偏弱（迭代 SHA-256 而非 PBKDF2）；证件备份信封使用全局固定盐（同口令跨用户彩虹表）；Keystore 损坏时 PIN 派生兜底密钥同样固定盐且**从未被接线**（设计存在但不可用）。
- **蓝队中危 2 项**：限流器使用墙钟可被时间回拨冻结；证件存储损坏后静默清空存在数据丢失路径。
- **用户体验高危 1 项**：网络故障被一律误报为"车次不存在或当日不开行"，离线场景下是致命误导。
- **用户体验中低危 6 项**：深色模式对比度、空输入无反馈、更新页死按钮、GPS 高频轮询耗电、PIN 对话框无失败反馈、异常原文直接上屏。

本轮已修复 **14 项**（红队 6、蓝队 3、UX 5），其余 3 项为需要平台工程或上游配合的待办，均已给出处置建议。

**二轮加固（同日 §8，应用户要求）**：Zero-Trust 会话边界（5 分钟授权过期）、硬件加密可探测（安全存储自检 + 姿态面板）、Passkey 姿态分级、CI 门槛精细化（8 模块覆盖率棘轮 + l10n 棘轮门禁，新增 22 个单测）、i18n/l10n 审查（597 处债务清单 + RTL 修复）。

## 1. USER 用户体验审计（可用性评估）

### U-01【高危】网络错误被误报为"车次不存在"
- **位置**：`lib/features/train/train_result_page.dart`（`snap.hasError` 分支）
- **现象**：`fetchOnline` 的任何异常（DNS 失败、超时、WAF 拦截、HTTP 5xx）都进入同一个 "404 车次不存在或当日不开行" 界面。用户在弱网/离线时会被误导为"车次停开"，做出错误出行决策——对铁路查询工具而言属于功能性误导。
- **本轮修复** ✅：区分 `TrainNotFoundException` 与 `DioException`（超时/连接失败/服务端错误分别提示），网络类错误展示 `wifi_off` 图标 + 人话文案 + 重试按钮；HTTP 404 响应仍归入"不存在"语义。

### U-02【中危】查询确认键对空输入无反馈
- **位置**：`home_page.dart` `_buildQueryTab` `onConfirm`
- **现象**：键盘输入为空时点确认直接 `return`，无任何提示，用户会认为按钮坏了。
- **本轮修复** ✅：空输入时弹出 SnackBar「请先输入车次号」。

### U-03【中危】实时测速页深色模式对比度不足 + GPS 轮询耗电
- **位置**：`lib/features/sensor/speed_page.dart`
- **现象**：硬编码 `Colors.black54` / `Colors.black45` 在深色主题下几乎不可见；`getCurrentPosition` 以 500ms 定时轮询，且单次定位耗时可能超过 500ms 造成请求堆叠，持续高精度定位会显著耗电。
- **本轮修复** ✅：文字颜色改用 `colorScheme.onSurfaceVariant`（随主题自适应）；轮询间隔放宽到 1s 并加在途互斥标志（上一拍未返回不发起新一拍）。

### U-04【中危】更新页"立即更新"是死按钮 + 原始异常上屏
- **位置**：`lib/features/oobe/update_page.dart`
- **现象**：`onPressed: () {}` 占位无任何行为；`_error` 直接拼接异常原文（含内部域名/Dio 细节），既不可用也泄露内部信息。
- **本轮修复** ✅：有下载地址时校验 `https` 后复制到剪贴板并提示"请在浏览器打开"；无地址时禁用按钮并说明；异常分类为人话文案（超时/断网/服务不可用），不再外泄内部细节。

### U-05【中危】PIN 回退对话框无失败反馈
- **位置**：`certificates_page.dart` `_pinFallback`
- **现象**：输错 PIN 对话框直接关闭，回到"通行密钥未授权"页，用户不知道输错了还是系统坏了，也没有剩余尝试次数提示。
- **本轮修复** ✅：对话框内联显示失败原因；连错触发锁定时显示解锁时间（配合 R-02 的锁定机制）；支持原地重试。

### U-06【低危·待办】l10n 覆盖率低
- **现象**：脚手架已接 `AppLocalizations`（5 语言），但大量 UI 字符串硬编码中文（测速页、更新页、证件页、设置页等）。多语言用户将看到混合语言界面。
- **处置** 📋：Phase 4 做 1:1 业务对照时统一抽取 `.arb`；本轮修复新增的文案沿用中文硬编码以保持一致，待统一迁移。

### U-07【低危·记录】证件页信息架构良好
- 分组（一人多证）、脱敏展示（`_mask`）、临期/过期分级提示、同号冲突告警、MRZ 校验位可视化等设计到位，属于加分项，无需改动。

## 2. 蓝队审计（防御纵深）

### B-01【中危】限流器依赖墙钟
- **位置**：`lib/core/network/rate_limiter.dart`（`DateTime.now()` 计算补充令牌）
- **风险**：系统时间回拨可使 `_lastRefill` 恒为"未来"，`elapsed <= 0` 短路导致令牌永不补充（自锁）或被恶意回拨刷桶（WAF 合规失效）。项目里明明已有 `TrustworthyClock` 的同类教训。
- **本轮修复** ✅：改用 `Stopwatch` 单调时钟计算流逝时间。

### B-02【中危】证件Prefs存储损坏后静默清空
- **位置**：`certificate_repository.dart` `PrefsCertificateStorage._read`
- **风险**：JSON 损坏（半写、存储坏块）时返回空 map，下一次 `store()` 会用只含新证件的 map **覆盖**主键，旧密文彻底丢失且无留档。
- **本轮修复** ✅：损坏数据先隔离到带时间戳的 `.corrupt.<ts>` 键再返回空库，为人工恢复保留现场。

### B-03【低危】离线库 LIKE 通配符未转义
- **位置**：`offline_db.dart` `buildTrainPreselectSql`
- **风险**：单引号已正确双写，无 SQL 注入；但 `%`/`_`/`\` 未转义，用户输入可注入 LIKE 通配符导致全表扫描式匹配（性能与结果准确性问题）。
- **本轮修复** ✅：转义 `\` `%` `_` 并为每条 LIKE 追加 `ESCAPE '\'` 子句；新增单测。

### B-04【低危·待办】无证书锁定（Certificate Pinning）
- **风险**：Android 用户 CA 证书可被中间人截获 TLS 流量（Dio 默认信任系统 CA 库）。当前仓库尚未生成 `android/`/`ios/` 平台工程，无法落地原生 network security config / ATS 例外。
- **处置** 📋：`flutter create` 生成平台目录后，在 Android `network_security_config.xml` 停用用户 CA、iOS ATS 收紧，并对 `*.zenglingkun.cn` / `*.railgo.dev` 评估公钥锁定。

### B-05【记录】依赖与密钥卫生
- 无硬编码生产密钥；`flutter_secure_storage` 配置正确（Android encryptedSharedPreferences、iOS first_unlock_this_device）；SM4 实现含 PKCS#7 校验与 IV 随机化，CBC 模式 IV 随密文前置存储，均符合规范。依赖全量宽松协议（CI license-scan 门禁在位）。

## 3. 红队审计（攻击模拟）

### R-01【高危】服务源 URL 无协议校验 → 传输降级攻击
- **位置**：`api_client.dart` `_normalizeBase`（仅去尾斜杠）、`service_registry.dart` `parseServiceEndpoints`（不校验返回 URL）
- **攻击链**：服务发现接口或未来的"自定义服务源"一旦返回/保存 `http://`（或 `file://`）地址，所有 API 流量——包括 `checkAuth` 的 `userid`/`key`——将以明文出网。控制网关或能篡改配置的攻击者可静默收割卡密与查询流量。
- **本轮修复** ✅：新增 `sanitizeServiceBaseUrl()`（强制 `https`、拒绝 userinfo、要求非空主机、容忍尾斜杠）；`baseFor()` 对覆盖值与缺省值统一过校验；服务发现解析跳过非法 URL；请求期校验作为纵深防御兜底。

### R-02【高危】PIN 验证无尝试限制 → 6 位数字穷举
- **位置**：`auth_gate.dart` `verifyPin`
- **攻击链**：拿到已解锁手机（或生物识别被禁用场景）的攻击者可在 UI 上无限次尝试 6 位 PIN（10^6 空间），平均 50 万次即可命中；无任何锁定或退避。
- **本轮修复** ✅：连续 5 次失败锁定 30s，之后指数退避（30s→1m→2m→4m→8m→15m 封顶）；锁定期间即使 PIN 正确也拒绝；验证成功或重设 PIN 清零计数；锁定状态与剩余次数暴露给 UI。

### R-03【中危】PIN 哈希选型：迭代 SHA-256 → PBKDF2
- **位置**：`auth_gate.dart` `PinHasher`
- **风险**：v2 使用"SHA256 迭代 10 万轮"（每轮单次压缩），对 GPU/ASIC 暴力破解的抵抗力弱于标准 PBKDF2-HMAC-SHA256（每轮约 4 次压缩 + 标准 KDF 语义）。拿到 root 后的 SharedPreferences 副本可离线穷举。
- **本轮修复** ✅：升级 v3 = PBKDF2-HMAC-SHA256（100k 轮，32 字节输出）；v1/v2 旧哈希验证通过后**透明升级**（用户无感，与既有 v1→v2 机制同构）；恒时比较保留。

### R-04【中危】备份信封全局固定盐
- **位置**：`certificate_repository.dart` `_backupKey`（salt 恒为 `railgo.cert.backup.v1`）
- **攻击链**：所有用户的导出信封使用同一盐。攻击者可预计算"常见口令 → 信封密钥"彩虹表，批量解密社工库流出的备份文件（导出文本质地天然易外泄）。
- **本轮修复** ✅：每次导出生成 16 字节随机盐并写入信封元数据（`v:2`）；导入时优先读取信封盐，缺失时回退旧固定盐（向后兼容 v1 信封）。

### R-05【中危·设计缺陷】Keystore 损坏的 PIN 派生兜底从未接线 + 固定盐
- **位置**：`key_service.dart`（`pinFallback` 参数）；`home_page.dart` 两处 `SecureStorageKeyService()` 均未传 PIN
- **风险**：代码注释宣称"Keystore 损坏时 PIN 派生兜底"，但生产装配从未传入 `pinFallback`，真实损坏路径只会抛 `StateError`（行程板红屏/证件读取失败）——**兜底不可用**。且派生盐为全局固定值，跨用户彩虹表风险同 R-04。另外 PIN 明文并不留存，即使想传也无从获取。
- **处置** 📋（需专门设计，建议方案）：设置 PIN 时额外生成"密钥包裹层"——`wrapped = SM4-CBC(PBKDF2(pin, per-install-salt), master_key)` 存入 SharedPreferences；Keystore 失效且用户通过门禁时解包裹恢复主密钥。这样既可用又避免固定盐。已作为 Phase 4 待办记录，本轮不动（避免半成品引入数据兼容风险）。

### R-06【低危】未过门禁的 `CertificateRepository.delete` 兼容方法
- **位置**：`certificate_repository.dart`（`delete(id)` 直接调 `storage.remove`）
- **风险**：与"任何删改必须过门禁"的红队规则相悖；当前无 UI 调用，但作为公共 API 是未来的绕过入口。
- **本轮修复** ✅：删除该方法（`deleteSecure` 是唯一删除路径）。

### R-07【低危·上游约束】卡密鉴权凭据走 GET 查询串
- **位置**：`railgo_api.dart` `checkAuth`（`?userid=&key=`）
- **风险**：查询串会进入服务端访问日志、网关日志，泄露面大于 POST body。该端点为上游既有契约（`center.zenglingkun.cn/beta`），客户端单方面改 POST 会破坏兼容。
- **处置** 📋：向上游提议支持 POST/头域鉴权；客户端在服务端支持后切换。R-01 的强制 HTTPS 已将传输层泄露面收敛为"服务端日志"。

### R-08【低危·接受】本地授权标记可被 root 篡改
- `jqok` / `AuthTime` 存于 SharedPreferences，root 设备可直接改写。客户端许可校验对 root 设备本质不可防御，属接受风险；线上服务端仍可持续复验。

### R-09【低危】导出密文经剪贴板外传
- **风险**：复制到剪贴板的备份密文可被输入法/云剪贴板同步。Android 10+ 已限制后台读取，iOS 为系统级剪贴板。
- **本轮修复** ✅（缓解）：复制成功提示明确告知"剪贴板可能被其他应用读取，请尽快粘贴并清除"，引导用户知情操作。

## 8. 二轮加固：Zero-Trust / 硬件加密 / Passkey / CI 精细化 / i18n（同日，应用户要求）

### 8.1 Zero-Trust：会话授权不再终身有效
- **ZT-1**：`SessionAuthGate` 新增 `maxUnlockAge`（默认 5 分钟，可注入时钟）。授权过期后**静默失效**，下一次读/写/删/导出必须重新通过生物识别/PIN——消除"解锁一次、全程裸奔"的窗口。单测覆盖：窗口内复用、超时重认证、手动 lock、null 兼容四种路径。
- **ZT-2**：既有规则保持并强化：仓储层每个敏感操作仍逐项消费 `GateResult.passed`（§2.1/红队规则），会话缓存只是 UX 优化且现在有时限。

### 8.2 硬件级本地加密：事实澄清 + 可探测
- **事实**：SM4 主密钥的硬件包装由 `flutter_secure_storage` 平台层实现——Android Keystore（EncryptedSharedPreferences）、iOS Keychain（ThisDeviceOnly, first_unlock）、HarmonyOS 通用安全存储。这部分**不是应用代码能"再打开一层"的开关**，代码层的职责是：装配正确选项（已正确）+ 探测可用性（本轮新增）。
- **HW-1**：`SecureStorageKeyService.selfTest()`——独立探测键读写删，不触碰主密钥条目；Keystore/Keychain 损坏时返回 false。
- **HW-2**：`kHardwareCryptoPostureNotes` 常量 + 证件页展示三端硬件加密事实（含"密钥绝不落明文盘"红线）。
- 遗留：R-05（Keystore 损坏后的包裹密钥恢复方案）仍为 Phase 4 待办，本轮自检使其至少可被发现并提示用户。

### 8.3 Passkey / 生物特征：姿态分级面板
- **PK-1**：新增 `SecurityPostureFacts` / `assessSecurityPosture` / `securityPostureAdvice`（纯逻辑）：
  - **硬件级加固**（hardened）= 安全存储自检通过 ∧ 已登记生物识别 ∧ 已设 PIN ∧ 会话自动过期；
  - **防护降级**（degraded）= 安全存储不可用（一票否决）或无任何可用门禁；
  - 其余为**标准防护**，附具体整改建议（登记生物识别/设置 PIN/启用会话过期）。
- **PK-2**：证件页"通行密钥"面板集成：自检 + 生物识别种类 + PIN 状态 + 分级图标与建议一览。
- 生物识别本体仍走系统级 local_auth（面容/指纹/虹膜 + 设备锁屏凭据回退），与一轮审查结论一致。
